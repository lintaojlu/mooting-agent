# 记忆底座选型对比

访问日期：2026-11-18。结论只采用当天打开的官方文档或官方 GitHub。`research/open-memory-systems.md`（访问 2026-11-12，时延修订 2026-11-13）只作索引。对不上的地方在第 2、3 章标出。第三方整理页 `neoneye.github.io/agent-memory-atlas` 本次不引用。

时延数字是建议验收线，不是这七个项目的实测承诺，也不是 MootingAgent 的性能承诺。

## 1. 项目需求和要求

MootingAgent 是单 Session 原型。眼镜是交互终端，记忆服务放在本地主机侧。技术栈是 Node.js `>= 24.9`（`README.md`）。记忆底座若是 Python 或 Go 服务，就多一个进程：Router/Context 用 HTTP 或 SDK 调用它，热路径上要算进序列化、网络和对方进程排队。

### 1.1 本次要满足的三条

1. **持续文本流。** 语音走火山双向流式 ASR（`README.md` 的 sound2text，接口说明指向火山官方文档）。播放后持续上传音频、持续识别。临时字幕会修订。只有收束后的定稿可以进入长期记忆，也可以交给 Router。持续识别本身不把每个分句交给 Router：按钮后的语句收束、约 1.5 秒静默后的尾部定稿、手动结束，才合并成一次提交；暂停、断线和超过 3 秒未定稿会中止，不把残缺文本自动交给 Router。
2. **后台整理。** 抽取、压缩、去重、冲突合并、摘要、索引维护放在用户请求之外。整理可以慢，可以占用空闲算力，不能卡住当次提问。
3. **分层存储，平行投影。** 同一条记忆同时保留：最近原文 / 工作记忆、可读页面或摘要、带版本的结构化事实、向量，图可选。这几份表示一起存在，检索不排成「先 RAM、再文档、再 SQL、再向量」的等待链。刚写入、尚未整理完的定稿必须立刻能读。

### 1.2 项目里已经写明的约束

来源是仓库 `README.md`，以及 `research/open-memory-systems.md` 2026-11-13 的时延修订。下面是重述。

- **本地部署。** 浏览器只连本地服务。账号数据落在 `data/<用户名>/`，账号之间隔离。公网入口另有登录；不设置公网变量时只听 `127.0.0.1`。
- **中文语料。** 交互、字幕和要记住的事实以中文为主。embedding 必须在中文上可用，不能只靠英文模型碰运气。
- **检索时延优先于把部署做轻。** 建议目标：RAM 活跃包 P95 ≤ 10 ms；一次混合召回 P95 ≤ 100 ms、P99 ≤ 200 ms；定稿从进入服务到可读覆盖层可见 P95 ≤ 100 ms，这段不等待 LLM 整理。深度召回另计预算，不挡住第一批结果。这些线还要按实际硬件、记忆规模和眼镜到主机的网络再校准。
- **热路径不依赖生成式 LLM。** 不把 LLM query rewrite、LLM rerank、agentic 多轮检索当作眼镜首包的唯一路径。常驻的小型 embedding 可以在线算；cross-encoder 只有实测进预算才用。
- **Context 还没有长期记忆。** `README.md` 写明 Context 只做结构化包装，没有长期记忆或知识图谱。Session 和任务在内存里，重启清空。模型配置在 `.env`。原始音频只留有限传输缓冲，不长期落盘。
- **控制权在 Router/Context。** 记忆的写入、失效和注入由这一层决定。不把控制权交给会自己改记忆的外部 Agent runtime。Worker 不直接回复用户。

底座的写入入口是收束后的定稿事件。临时 ASR 只留在字幕。未整理完的定稿先出现在本进程可读覆盖层；抽取和合并在队列里做完，再发布摘要、事实版本和向量。

## 3. 分析及结论

用什么做底座：**MootingAgent 自建追加日志、后台整理队列和分层只读投影。** 七个项目都不直接接上当整套底座。

整理引擎先只做两个 PoC，不要七个同时接进热路径。

- **Hindsight**：后台整理的首选候选。observation 合并、带证据、mental model / pages 可后台更新，读取 mental model 不调 LLM，事实能留中文原文，存储是 SQL + pgvector。完整 recall 含 cross-encoder，放在第二级并设 deadline。
- **EverOS（原 EverMemOS）**：对照候选。Markdown、SQLite、LanceDB 已经是「页面 + 结构化状态 + 向量/BM25」三层，推荐的 Qwen3 embedding 面向多语言。`keyword` 与配好 embedding 的 `hybrid` 可以不走生成式 LLM。它的缓冲、边界 LLM 和索引滞后，解决不了定稿立刻可读。
- **Mem0 OSS、LangMem、Cognee**：只作整理算法候选，不进第一轮双 PoC。Mem0 的 add 是一次 LLM 抽取，search 默认可不调 LLM，但 v3 不再合并旧事实，图也不在 OSS 里。LangMem 的 background manager 适合嵌进自建队列，存储得自己带。Cognee 的图和 `improve` 适合慢整理；配了 LLM 时默认 recall 含一次生成，热路径若要用，必须钉住 `only_context` 或非 completion 类型并先测时延。
- **WeKnora**：文档知识库。长期记忆是短条目、有帽、对话后延迟抽取，嵌在平台回答链路里。
- **Supermemory**：摄入队列是清楚的，搜索也不等队列。默认 embedding 是英文专用模型。换成 `bge-m3` 或同等模型并完成中文召回测试之前，不进入锁定名单。默认 dynamic dreaming 还会让档案和记忆晚于文档索引。

这个排序仍是 2026-11-13 的「先 PoC Hindsight 与 EverMemOS，热路径自建」。依据是本次官方页仍支持该分工：两者都有「慢整理 + 一条不调用生成式 LLM 的读路径」，其余五个要么把 LLM 放进默认读，要么没有冲突合并，要么包着整套 RAG/Agent，要么默认英文向量。变的是 EverOS 的存储形态，以及 Mem0 不再够格当合并器。没有把 Hindsight / EverOS 升成已经锁定的引擎，因为时延都还没在本仓库量过。

### 3.1 推荐形态

```text
定稿事件 → data/<用户名>/ 追加日志
        ├─ RAM 覆盖层（原文、人物卡、当前任务）立刻可读
        └─ 单条后台队列
              抽取 / 去重 / 冲突合并 / 摘要 / 索引
              → 只读投影：页面、事实版本、向量、可选图
眼镜提问 → 先读 RAM
        → 预算内并行：关键词 + 结构化过滤 + 向量
        → 超时则取消慢分支；深度反思另送，不挡首包
```

Router/Context 决定写入和注入。整理器只消费定稿，不接收临时字幕，也不在热路径里改写用户请求。Python 或 Go 引擎以侧车运行，用用户名做 bank / user_id / namespace。投影发布带版本；删除和纠正要同时打到 RAM 和索引，避免旧事实被缓存送回。

同一阶段只接一个整理器。Hindsight 和 EverOS 分两轮对照，不并行双写，避免两套抽取和两套向量。

### 3.2 第一阶段 PoC 与锁定线

PoC 做三件事。

1. 自建定稿日志和 RAM 覆盖层。输入用中文定稿事件，包含临时修订被丢弃、暂停不提交、同一句被改写。覆盖层在整理开始前就可读。
2. Hindsight 轮：后台 `retain`；热读只读 mental model / page；完整 recall 作为可取消的第二级。顺带量 `chunks` 模式是否让原文在抽取前可被 recall 读到。
3. EverOS 轮：后台 `add` + `flush`；热读用 `keyword`，以及换上 `Qwen/Qwen3-Embedding-4B`（或同级中文模型）后的 `hybrid`。`agentic` 和 `llm_multiround` 不进首包。记录 flush 返回到搜索可见的滞后。

两轮用同一批中文用例：人物提醒、刚才说的话、事实纠正、跨会话回忆、场景切换、删除后仍被召回。每种都跑空闲、后台整理打满、冷启动、短时突发。

锁定引擎要同时满足：RAM 活跃包 P95 ≤ 10 ms；混合召回 P95 ≤ 100 ms、P99 ≤ 200 ms；定稿可读 P95 ≤ 100 ms，且这段没有等待 LLM。另外报告事实是否召回、纠正是否生效、删除是否立刻消失、后台满载时热路径是否被拖慢。有一项不达标，就留下它的整理能力，检索继续自建，不把整套产品换进 Router。

Mem0、LangMem、Cognee 只在两个 PoC 的整理质量都不够时，再单选一个做抽取/合并实验。Supermemory 只在多语言 embedding 换好之后单开一轮。WeKnora 不进这条 PoC。

### 3.3 与 2026-11-13 调研不一致的要点

- EverMemOS 仓库已 301 到 EverOS。主存储不再是 MongoDB + Elasticsearch + Milvus + Redis。默认是 Markdown + SQLite + LanceDB。Milvus 从 1.3.0 起只是可选派生索引。
- EverOS 没有把「embedding + BM25 + RRF、跳过 LLM」写成默认检索。默认 hybrid 依赖 embedding；跳过 LLM 的是显式 keyword。agentic 与 llm_multiround 会调 LLM。反思合并默认关闭。
- Mem0 OSS v3 只 ADD，不再 UPDATE/DELETE 合并。图记忆已从 OSS 移除。`AsyncMemory` 不是后台整理队列。平台基准分不等于 OSS。
- Cognee 默认库仍是 SQLite + LanceDB + Ladybug，Ladybug 即原 Kuzu。默认 recall 在配了 LLM 时仍是带生成的 `HYBRID_COMPLETION`。新增的是无密钥 GLiNER 路径，以及 Postgres 图演示（生产图能力为授权产品）。
- Hindsight 的整理/快读分工仍在。新增 2026-11-03 的决策、重排、embedding 模型；完整 recall 仍含 cross-encoder。
- Supermemory 默认英文 embedding 仍在，并写了正式警告和 `bge-m3` 换模方法。摄入队列已确认，搜索不等待入库。官方配置页只写加密快照，未点名 SQL 引擎；仓库 issue #1366 将其描述为嵌入式 PGlite（Postgres WASM，默认 memFS）加 pgvector / HNSW。
- WeKnora v0.8.0 日期 2026-09-03、记忆类别、300 字、200/2000、auto 延迟、consolidate、pending 不进提示词，均与事先线索一致。不一致处：记忆表同时有 Postgres 和 SQLite 迁移，Neo4j 与 MinIO 是可选 profile，不是记忆功能的硬前置；「约 5 条、600 字」未在打开的官方页出现。

### 3.4 仍未核实

- WeKnora 提示词预算「约 5 条、600 字」。
- 源码符号 `memory consolidator`。已核实的对应发布说明叫 Context Compaction，压缩的是沙箱工具历史。
- Hindsight 八种语言的名单，以及 `hs-embed-1` 在中文上的召回。Node 嵌入式入口是否另起进程。
- LangMem Memory API reference 页的逐项签名。
- Cognee 无密钥路径的本地 embedding 模型名。
- Mem0 混合检索有没有现成的中文 spaCy / 中文分词配置。
- Supermemory 的 SQL 引擎名。配置页只写加密快照；PGlite 来自仓库 issue #1366，不是产品文档的点名。
- 上述全部时延，包括 Supermemory 档案「约 50 ms」、EverOS「亚秒到 10–15 秒」。这些是对方文档里的数字，本仓库未测。
